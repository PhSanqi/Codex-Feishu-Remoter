# CFR M2 Feishu Gateway Architecture

M2 adds a direct Feishu-to-CFR surface. Broker, Router, Workspace Arbitrator, RouteBinding, and cross-system workspace leases remain out of scope.

```text
`lark-channel-sdk` / `FeishuChannel`
        |
        v
Channel SDK normalized message/card event
        |
        v
FeishuGateway: parse -> authorize -> inbox INSERT OR IGNORE -> enqueue -> return
        |
        v
FeishuStore / durable inbox / session binding / daemon lease
        |
        v
FeishuDaemon: worker queue + per-chat serialization + stop control lane
        |
        v
one long-lived CodexAdapter instance
        |
        v
fresh CFR-owned app-server per Codex operation
```

The Channel SDK owns WebSocket lifecycle, reconnects, bot identity, exact `mentioned_bot`, official normalized `content_text`, card actions, and outbound send/reply. CFR maps `content_text` into its neutral `body_text`/`text` fields and retains the latter only as a legacy fixture fallback. Card messages use the SDK's explicit `{"card": card_payload}` shape, and CFR marks delivery sent only after a successful `SendResult` with a message ID. Approval cards are generated by one CFR Approval Card JSON 2.0 builder: legacy `tag:"action"` containers are forbidden, buttons use `tag:"button"` plus callback behaviors, and callback values contain only bounded `action`/`approval_id` identity fields. A failed card send is a hard delivery failure and resolves the approval fail-closed to decline; it is never presented as an approval wait or business pass. CFR does not inspect raw typed `lark-oapi` events. CFR waits for the SDK's own `connect_until_ready` and `is_ready` contract; it never publishes a local early-ready signal. The callback never waits for a Codex turn or outbound API call. `message_id` is the inbound idempotency key. Outbound replies use deterministic UUIDs derived from `message_id`, phase, and chunk index.

Normal prompts are serialized per Feishu chat. `/cfr stop` uses the control lane and does not wait behind the normal prompt lock. A daemon owns one Channel SDK transport lease per app namespace and one CodexAdapter instance; the transport runs its asyncio loop in a dedicated thread and uses bounded `run_coroutine_threadsafe` calls for worker-thread outbound delivery. The normal CLI remains blocked until Ctrl+C, a transport failure, or daemon lease loss. The existing CFR thread runtime lease remains a separate per-native-thread writer fence.

## Feishu SDK Runtime Boundary

The transport thread performs synchronous SDK import, compatibility inspection, `FeishuChannel` construction, and handler registration before creating CFR's asyncio loop. Only then does it run `connect_until_ready`, publish `READY`, and wait for shutdown. This prevents a Channel SDK module-global WS loop from capturing an already-running CFR loop. The isolated `sdk_compat` adapter is feature-detected and removable; it does not mutate site-packages, call `nest_asyncio`, or create a second live transport path.

Shutdown is the reverse lifecycle boundary: stop callback acceptance, signal
the async shutdown event, let the CFR phase return, run
`shutdown_asyncgens`, close the CFR loop, and only then invoke the SDK public
`disconnect()`/`stop()` lifecycle on a fresh non-CFR loop. The feature-detected
`sdk_compat` boundary drains only SDK-owned WS/cache tasks and records closed
or running-loop diagnostics; it never cancels unrelated tasks or awaits SDK
private coroutines. SDK logging defaults to `WARNING`, with an explicit
`CFR_FEISHU_SDK_LOG_LEVEL` override limited to `WARNING`, `ERROR`, or `INFO`;
captured diagnostics are sanitized before output.

Feishu App ID is persisted in the platform CFR config directory and App Secret
in the OS keyring. Environment variables override persistent values for CI or
debugging. The CLI, doctor, and all live probes use the same resolver; no
plaintext secret-file fallback exists.

M2 V1 supports text messages, private chats, and opt-in group/topic mentions. Unknown chat types are ignored. Sessions are keyed by `chat_id` and bind at most one native CFR thread. A pending `/cfr new` session uses the next normal message as the first Codex turn, avoiding an extra initialization turn.

Restart recovery is fail-safe: queued inbox rows are re-enqueued, running rows become `interrupted_on_restart`, and pending approvals become `orphaned`. Running Codex work is never replayed automatically.

Desktop continuity follows M1. Feishu writes the same native Codex thread and marks `desktop_sync_state=refresh_required`; M2 does not implement Desktop push to Feishu.

## Normal Turn Progress

App-server RPC acknowledgements retain their short 30-second timeout. A normal
Codex turn has a separate 1800-second execution timeout, so the acknowledgement
boundary is not misclassified as a complete-turn deadline. While a turn is
active, Feishu sends one ephemeral progress card and updates that same card at
a throttled cadence. It can show turn state, `/steer` availability, a native
reasoning-summary projection, generic tool stage, and a bounded answer preview.
It never exposes raw reasoning deltas, raw tool payloads, commands, or secrets.
Progress state is not stored; the native Codex thread remains the durable
authority. Card delivery failure is UX-only and cannot fail the Codex turn. A
completed turn still sends its complete final answer through the normal Feishu
text-reply path; failed, stopped, or timed-out turns are not presented as a
successful partial answer.
